# Архітектура

Монолітний вебзастосунок на Django із серверним формуванням сторінок.
Окремого фронтенд-фреймворку немає: для цієї задачі він не потрібен,
а один застосунок простіше запускати й перевіряти.

```
Браузер ──HTTP──▶ Django (config/urls.py)
                    ├── catalog/views.py   сторінки каталогу
                    ├── bookings/views.py  оформлення й перегляд заявок
                    ├── bookings/manager_views.py  панель менеджера
                    └── admin              адміністрування
                          │
                          ▼
                  bookings/services.py     бізнес-правила
                          │
                          ▼
                  Django ORM ──SQL──▶ PostgreSQL 16
                                       ├── CHECK-обмеження
                                       └── EXCLUDE USING GIST (заборона перетину)
```

## Модулі

| Модуль | За що відповідає | Ключові файли |
|---|---|---|
| `config` | Налаштування, підключення до БД, маршрути верхнього рівня | `settings.py`, `urls.py` |
| `accounts` | Модель користувача з роллю (клієнт / менеджер), реєстрація клієнта | `models.py`, `forms.py`, `views.py`, `admin.py`, `tests.py` |
| `catalog` | Типи обладнання, екземпляри, тарифи; сторінки каталогу; календар доступності; демо-дані | `models.py`, `views.py`, `availability.py`, `management/commands/seed_demo.py`, `seed_loadtest.py` |
| `bookings` | Бронювання, журнал подій, усі правила зміни бронювань; сторінки заявок | `models.py`, `services.py`, `forms.py`, `views.py`, `manager_views.py`, `tests.py` |
| `templates` | HTML-шаблони сторінок | `base.html`, `catalog/*.html`, `bookings/*.html`, `registration/*.html` |
| `static` | Таблиця стилів | `css/site.css` |
| `loadtest` | Сценарії навантажувального тестування | `locustfile.py` |

## Де перевіряються правила

| Правило | Де | Чому там |
|---|---|---|
| Перетин періодів одного екземпляра | PostgreSQL (`booking_no_overlap_per_unit`) | Лише СКБД гарантує правило для одночасних запитів |
| Дата повернення > дати видачі | PostgreSQL (CHECK) + `services.validate_period` | БД — остання лінія захисту, сервіс — зрозуміле повідомлення |
| Минула дата, стан екземпляра, наявність тарифу | `services.create_booking` | Залежить від поточної дати й інших таблиць |
| Зміни бронювань в адмінці | Адмінка показує бронювання лише для перегляду (`BookingAdmin`) | Пряме редагування обійшло б перевірки, журнал подій і розрахунок доплати |
| Хто може змінити статус і на який | `services.check_transition` (використовують і `change_status`, і кнопки) | Залежить від ролі, власника заявки й дати |
| Одночасні дії над однією заявкою | `SELECT ... FOR UPDATE` у `change_status` і `extend_booking` | Друга дія бачить уже змінений стан |
| Видача неповерненого екземпляра | `services.check_transition` (`unreturned_booking`) | Залежить від стану інших бронювань екземпляра |
| Доплата за запізнення | `services.calculate_late_fee` під час переходу в `returned` | Залежить від фактичної дати |
| Взаємне блокування при одночасному створенні | повтор спроби в `create_booking` | PostgreSQL перериває одну з транзакцій; повтор перетворює це на зрозумілий конфлікт |

Код, що змінює бронювання, має викликати функції з `bookings/services.py`,
а не змінювати модель напряму: інакше не запишеться журнал і не перевіряться права.

## Інтерфейс

Сторінки формує сервер (шаблони Django), окремого фронтенд-фреймворку немає.
JavaScript використано лише для попереднього розрахунку вартості у формі
бронювання й підтвердження скасування; без нього все працює (вартість однаково рахує сервер).

**Стилі.** Один файл `static/css/site.css`. Усі кольори задано CSS-змінними.
Світла й темна теми перемикаються автоматично за налаштуванням операційної
системи (`prefers-color-scheme`), окремого перемикача немає.
Статичні файли віддає WhiteNoise, тому стилі працюють і без режиму налагодження
(наприклад, під Waitress під час навантажувального тестування).

**Адаптивність.**
- Ширина вмісту обмежена 1120 px.
- Каталог і календарі будуються сіткою `auto-fill`, тож кількість колонок залежить від ширини екрана.
- Двоколонкові сторінки на ширині до 860 px стають одноколонковими.
- На ширині до 720 px таблиці перетворюються на картки: підпис кожного поля береться з атрибута `data-label`.
- Перевірено на ширині 1280 px і 390 px (типовий телефон).

**Сторінки помилок.** Для кодів 400, 403, 404 і 500 є власні шаблони українською
(`templates/400.html` … `500.html`) в оформленні сайту, тож користувач не бачить
стандартних англомовних сторінок Django. Шаблон 500 не наслідує `base.html`: під час
помилки сервера контекст запиту (користувач, меню) може бути недоступний.

**Доступність.**
- Семантична розмітка: `header`, `nav`, `main`, `footer`, `table` з `th scope`.
- Посилання «Перейти до вмісту» для навігації з клавіатури.
- Видимий фокус (`:focus-visible`).
- `aria-current` для активного пункту меню й вкладки, `aria-label` для навігації та полів без видимого підпису.
- Підписи `label` для всіх полів форм; повідомлення з `role="status"`.
- Стан дня календаря передається не лише кольором, а й підказкою (`title`) і штрихуванням для перерви.
- `prefers-reduced-motion` вимикає анімації.
